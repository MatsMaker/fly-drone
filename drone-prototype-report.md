# Звіт: Unity-прототип польоту дрона

Архітектура прототипу: які підсистеми є, за що кожна відповідає і як вони взаємодіють.

---

## 1. Загальна схема

```
Input → DroneInput ─┐
                    ├─► FlightController ─► DronePhysics (Rigidbody) ─► Transform
Stabilizer (PID) ───┘                                │
                                                     ▼
                                          CameraFollow / HUD
Terrain: TerrainStreamer ─► Chunks (LOD, culling, pooling) ◄── позиція дрона
```

Головний принцип: **ввід нічого не рухає напряму** — він лише задає бажання (throttle, pitch, roll, yaw). Рух виникає виключно з сил, прикладених до `Rigidbody`.

---

## 2. Фізика польоту

### 2.1 Rigidbody

Один `Rigidbody` на кореневому об'єкті дрона. Усі розрахунки — у `FixedUpdate()`, щоб фізика не залежала від FPS.

Налаштування:

- маса ~1–2 кг, `useGravity = true`;
- `Interpolation = Interpolate` — плавна картинка між фізичними кроками;
- `Collision Detection = Continuous Dynamic` — щоб на швидкості дрон не пролітав крізь terrain;
- `Drag` / `Angular Drag` мінімальні (опір рахуємо самі).

### 2.2 Тяга (thrust)

Квадрокоптер має 4 ротори. Кожен створює силу вздовж локальної осі «вгору» дрона:

```csharp
rb.AddForceAtPosition(transform.up * motorThrust, motor.position, ForceMode.Force);
```

- **Сумарна тяга** залежить від throttle (газу).
- **Різниця тяги між моторами** створює моменти: pitch (нахил вперед/назад), roll (вбік), yaw (розворот).
- `AddForceAtPosition` для кожного мотора дає реалістичну поведінку «з коробки»: нерівна тяга сама створює обертання.

Щоб дрон висів у повітрі: `hoverThrust = mass * g / 4` на мотор.

### 2.3 Інерція

Окремого коду для інерції не потрібно — її дає сам `Rigidbody`: маса, швидкість і `inertiaTensor`. Дрон не зупиняється миттєво, а розгойдується й ковзає.

Що можна налаштувати:

- `rb.mass` і `rb.inertiaTensor` — «важкість» реакції на повороти;
- **згладжування обертів моторів** (`Mathf.MoveTowards` від поточної тяги до цільової): мотор не розкручується миттєво, це додає відчуття ваги.

### 2.4 Опір повітря (drag)

Рахуємо вручну — це показує розуміння фізики краще, ніж стандартний `rb.drag`:

```
F_drag = -0.5 · ρ · Cd · A · |v| · v
```

- `ρ` — густина повітря (~1.225 кг/м³), `Cd` — коефіцієнт опору, `A` — площа.
- Векторна форма з `|v| · v` дає квадратичний опір: чим швидше, тим сильніше гальмує.
- Можна рахувати окремо для осей дрона (у локальних координатах): вперед опір менший, ніж убік чи вгору. Це створює природну максимальну швидкість.
- Те саме для обертання (angular drag), щоб дрон не крутився безкінечно.

### 2.5 Стабілізація (PID)

Реальні дрони мають польотний контролер. Без нього керувати сирою фізикою майже неможливо.

- **Режим Angle** (для початківців): стік задає *цільовий кут* нахилу, PID-регулятор рахує момент, щоб до нього прийти.
- **Режим Acro** (опційно): стік задає *швидкість обертання*.
- **Утримання висоти**: PID по вертикальній швидкості.

## 3. Розподіл відповідальності по скриптах

| Скрипт | Відповідальність |
|---|---|
| `DroneInput` | Зчитує Input System (клавіатура/геймпад), віддає нормалізовані значення осей. Нічого не знає про фізику. |
| `FlightController` | «Мозок»: перетворює ввід + стан дрона на цільову тягу кожного мотора. Містить PID. |
| `Motor` | Один ротор: поточна/цільова тяга, інерція розкрутки, візуальне обертання гвинта. |
| `DronePhysics` | Прикладає сили до `Rigidbody`: тяга від моторів, драг, гравітація. |
| `PIDController` | Універсальний регулятор (P, I, D, обмеження інтегралу). |
| `DroneCamera` | Камера від 3-ї особи з плавним слідуванням, опційно FPV. |
| `DroneHUD` | Висота, швидкість, тяга, FPS, режим польоту. |
| `DroneConfig` (ScriptableObject) | Усі параметри: маса, Cd, коефіцієнти PID, макс. тяга. Змінюється без перекомпіляції. |

Такий поділ показує чисту архітектуру (Single Responsibility) і дозволяє тестувати частини окремо.

## 4. Великий terrain і оптимізація

Ключова проблема: один величезний Terrain (наприклад, 4×4 км) дуже дорогий за пам'яттю й рендерингом. Рішення — багаторівневе.

### 4.1 Тайлинг (чанки)

Замість одного terrain — сітка з `Terrain`-тайлів (наприклад, 512×512 м кожен). `TerrainStreamer` слідкує за позицією дрона:

- тайли в радіусі N — **активні**;
- далекі — **вимкнені або вивантажені** (streaming).

Тайли з'єднуємо через `Terrain.SetNeighbors()`, щоб не було швів між LOD.

### 4.2 LOD і налаштування Terrain

- **Pixel Error** збільшити (5–10) — менше трикутників;
- **Basemap Distance** зменшити;
- **Heightmap Resolution** розумна (513 або 1025, не 4097);
- **Detail Distance** і **Tree Distance** обмежити, використовувати **GPU Instancing** для трави;
- **Trees**: близькі — меші, далекі — billboard.

### 4.3 Culling і рендер

- **Frustum culling** — стандартно; для тайлів додатково перевірка дистанції;
- **Occlusion culling** мало допомагає на відкритому terrain, тому головне — дистанційне відсікання;
- **Fog + Far Clip Plane** — приховують межу видимості й економлять рендер;
- **SRP Batcher / Instancing** для об'єктів навколо.

### 4.4 Пам'ять

- **Object Pooling** для дерев, каміння, ефектів;
- **Addressables** або `SceneManager.LoadSceneAsync(Additive)` для асинхронного підвантаження тайлів без фрізів;
- стиснення текстур (ASTC/DXT), **Texture Streaming**, mipmaps.

### 4.5 Проблема великих координат

Далеко від початку координат (10+ км) `float` втрачає точність, і фізика «тремтить». Рішення — **Floating Origin**: коли дрон віддаляється від (0,0,0), весь світ зсувається назад. Для тестового завдання достатньо згадати в README як відому проблему й зробити просту реалізацію.

## 5. Профілювання й доказ оптимізації

Це те, що виділяє серед інших кандидатів:

- знімки **Unity Profiler** до/після (CPU, GC Alloc, Draw calls);
- **Frame Debugger** — кількість батчів;
- **Stats** — Tris/Verts/SetPass calls;
- **FPS-лічильник** на екрані, метрики в README (наприклад, «було 45 FPS → стало 110 FPS при 16 км²»);
- відсутність GC-алокацій у `Update` / `FixedUpdate`.

```
  Scripts/

  Terrain/
```

## 7. Рекомендований порядок робіт (2 дні)

**День 1 — фізика:**
Rigidbody + 4 мотори → тяга й гравітація → драг → PID-стабілізація → камера й HUD.

**День 2 — світ і оптимізація:**
terrain-тайли → streaming за дистанцією → LOD/налаштування → Floating Origin → профілювання, скріншоти, README.

---

## 8. На що зазвичай дивляться при перевірці тестового

1. Чи керування «відчувається» як дрон (інерція, а не «літаюча коробка»).
2. Чи фізика в `FixedUpdate` і не залежить від FPS.
3. Чистота коду та розподіл відповідальності.
4. Чи є реальні цифри оптимізації, а не просто «я оптимізував».
5. Чи README пояснює рішення та обмеження.
